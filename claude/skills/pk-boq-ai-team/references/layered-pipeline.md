# 8 阶段分层流水线（模式 B）

> 大表（>500 行）+ 规则可脚本化 + 需要 LLM 语义判断的任务，强制按此拓扑执行。
> 源自 `pk-boq-classify` 的 team_pipeline，此处为不绑定场景的通用版。
> 核心是第 ② 步**脚本化路由**（纯代码 · 0 token）：先按规则判定，再检索候选，
> 按候选数分档，只把必要的行送 LLM，按候选数选便宜/贵的模型。

## 各阶段职责

| 阶段 | 模型/工具 | 职责 | 交接物 | 触发条件 |
|------|-----------|------|--------|----------|
| ① 离线校准 | Opus | 定归一化规则、检索策略、分档阈值、路由表、prompt 模板；**设计 sub-agent 最小上下文**（只带执行必需信息，不塞完整技能说明）；用黄金集校准 | 规则库 + 术语表 + 阈值 + 模板 + sub-agent prompt 最小集 | 一次性 / 每次规则更新 |
| ② 判定路由 | 纯代码 | 跳过/暂定金额/唯一命中判定；闭词表候选检索；按候选数分档 | route_result.json | 每次运行，0 token |
| ③ 轻量执行 | Haiku | 2-3 候选内做关键字+量纲敏感选择 | 执行结果 | LOW 档 |
| ④ 语义执行 | Sonnet | 4+ 多候选/近似项做语义推理，可拒绝（no_match） | 执行结果 | HIGH 档 |
| ⑤ 纯规则自动 | 代码 | 唯一命中/跳过/暂定金额项直接写回，不走 LLM | 直接写回结果 | UNIQUE/SKIP/SUM |
| ⑥ 一致性比对 | 代码 | ③④ 输出跨模型比对（真独立信号）；一致自动通过，不一致进冲突池 | 通过项 / 冲突池 | ③④ 有输出 |
| ⑦ 仲裁 | Opus（限量） | 只仲裁冲突 + 零候选异常；优先高风险/金额异常项 | 最终判定 + 理由 | 冲突池 / ZERO |
| ⑧ 回写 | Python + 人工 | 写回结果列 + 变更标记；生成报告；未决项进人工队列 | 已处理 xlsx | 全部 |

## 分档阈值（② 的产物，任务定制）

| 候选数 | 档位 | 处理 | 模型 |
|---|---|---|---|
| 0 | ZERO | 进冲突池/人工 | Opus |
| 1 | UNIQUE | 直接写回 | 无 |
| 2-3 | LOW | 关键字+量纲 | Haiku |
| ≥4 | HIGH | 语义推理可拒绝 | Sonnet |

阈值（2-3 边界）不是铁律，由 ① Opus 按任务规模/歧义度校准。候选不是"数量"而是"分部的候选数"时，同理。

## 成本控制要点

- 第 ② 步全程 0 token：判定 + 检索 + 分档都是代码。
- 唯一命中 / 跳过项 / 暂定金额项直接写回，不经过任何 LLM。
- 仅 LOW 调 Haiku、HIGH 调 Sonnet，按候选数选便宜/贵的模型。
- Opus 限量：只仲裁冲突池和零候选异常，不做常规执行。
- 人工确认结果沉淀回 ① 规则库/黄金集，下次运行自动复用，越用越准。

### Token 侧三项优化（ZOO 分类教训）

1. **按 token 预算切 slice，不按行数/章节切**。agent 每次调用有固定开销（system prompt + 任务说明 + 输出约束），slice 越小固定开销占比越高。按每 slice 预算（默认 50k）切，**同一分组（章节/子分部/说明）保持原子性不跨 slice**，在原子性前提下填满预算 → agent 数可砍半以上。
2. **裁剪 agent system prompt（① Opus 设计分派包）**。Sub-agent 不需要完整技能上下文——只需执行必需的**最小集**：闭词表（或池内候选）+ 行格式 + 输出约束 + 本批上下文。完整技能说明/方法论留在 ① 规则库和 ② 路由脚本层，不逐份拷贝给每个 agent。**谁设计这个最小集？① Opus**——只有校准阶段的设计者知道每个 agent 类型真正需要什么信息做决策、什么信息是噪音。Sub-agent 拿到的 prompt 是 Opus 预先裁剪过的"执行包"，不是完整 SKILL.md。
3. **仲裁只在分歧时触发**。⑥ 跨模型比对不是"全量双跑两模型"（那等于成本翻倍）。Haiku 出 conf≥阈值（如 0.6）直接过（可抽样复核），conf<阈值才升级 Sonnet；只有升级冲突项 + 零候选 + 高风险/金额异常才进 ⑦ Opus。

### 质量门禁：⑧ 写回前 dry-run 预检（ZOO 分类教训）

写回前必须出一份**行级映射覆盖率报表**，把断层堵在写盘前——而不是写回后发现再返工（ZOO 分类：B 册 903 行 unmapped、子分部"第X章"前缀不一致，全是写回后才发现）。

- **覆盖率**：每行是否有判定（分类/匹配/套价）→ unmapped 清单 + 按分组分布
- **闭词表校验**：判定值是否在允许值集合内（分类值/定额编码/价格单位），违规项标记
- **前缀一致性**：去前缀规则是否正确应用（子分部"第X章"）
- **脚本**：`scripts/dry_run_precheck.py`（通用，参数化结果/闭词表/分组字段）
- **门禁**：不通过 → 阻止写回，先补断层再写盘

## 与模式 A 的关系

8 阶段流水线是模式 A 里「流水线多轮 + 阶段内星型」的工程化深化：
- 阶段间：流水线多轮（下游依赖上游，Lead 逐阶段合成推进）
- 阶段内：星型单轮（③④ 执行层多个 agent 并行，彼此隔离，走 Lead 中转）
- 差别：模式 A 是"选个拓扑组织 agent"，模式 B 连"谁用哪个模型、怎么分档、冲突怎么办"都预设好了，任务方只需实例化 ② 的路由脚本和 ③④⑦ 的 prompt。
