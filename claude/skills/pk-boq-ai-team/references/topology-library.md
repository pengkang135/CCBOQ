# 6 种通用协作拓扑（模式 A）

> 底层分类：**子 Agent 之间是否有通信**。这是唯一分水岭——其他维度（Agent 数量、汇报方式、串并行）都是表象。

```
子Agent间无通信                              子Agent间有通信
────────────────────────────                ──────────────────────
Agent彼此隔离，信息全部走Lead中转             Agent之间直接对话，不经过Lead
Lead = 唯一信息交汇点 + 裁决者               Lead = 旁观者 / 顶层调度者 / 末端接收者
牺牲信息效率，换视角独立性                  释放协作灵活性，引入协调成本
```

## 一、无通信模式

### 星型单轮

```
         Lead
      ┌──┼──┐
      A  B  C  D     ← 彼此隔离，同一条消息并行启动
```

- **机制**：同一条消息并行启动 N 个 Agent → 各自独立完成 → 汇报给 Lead → 全部到齐后 Lead 综合裁决
- **耗时**：约等于最慢 Agent（全部并行）
- **适用**：多视角审视同一对象，各视角彼此独立、不需要互相知道
- **案例**：多语言翻译+审校、代码审查（安全/性能/可维护/可读）、竞品分析、论文盲审

### 流水线多轮

```
阶段一：N Agent 并行 → Lead 合成 → 阶段三：M Agent 并行 → Lead 定稿
```

- **机制**：下游阶段依赖上游产出，阶段间串行，阶段内并行。不同阶段 Agent 角色完全不同
- **耗时**：约等于各阶段最长 Agent 耗时之和
- **适用**：多阶段产出物交付，下游依赖上游结果
- **案例**：技术报告撰写（调研→合成→把关）、软件发布（开发→测试→文档→发布）、法律文书
- **→ 深化为模式 B**：当"规则可脚本化 + 需要 LLM 语义判断 + 大表"时，此拓扑深化为 8 阶段分层流水线（见 layered-pipeline.md）

### 数据采集器

```
        Lead（自己做全部分析判断）
      ┌──┼──┐
     采  采  采  采     ← 仅返回原始数据/素材，无分析无建议
```

- **机制**：Agent 不是团队成员，只是并行数据获取工具，返回原始数据，Lead 自己做全部分析和决策
- **适用**：纯信息搜集，分析和决策由人（或 Lead）完成
- **案例**：出差行程规划（航班/酒店/天气/交通/治安只返回事实）、学术文献综述、市场调研、故障排查日志采集

## 二、有通信模式

### 网状辩论

```
        A ←──→ B
        ↕       ↕
        C ←──→ D
             ↕
        Lead（旁听+裁决）
```

- **机制**：Agent 全连接互发消息，互相挑战对方命题和论据。Lead 旁观，最终根据辩论质量（而非立场）裁决
- **适用**：没有标准答案、需要正反碰撞的决策问题
- **案例**：技术架构选型（微服务 vs 单体 vs 云原生）、产品方向决策、法律策略
- **风险**：无尽辩论（需设轮次上限）、观点趋同（需安排对立立场）。建议 3-5 个 Agent

### 链式接力

```
A ──→ B ──→ C ──→ D ──→ Lead
```

- **机制**：单向链，上游产出直接传给下游作为输入，Lead 只在末端接收验收。每 Agent 只做一件事
- **适用**：单线程递增精炼，每一步输出天然是下一步输入
- **案例**：长文档翻译+润色（直译→术语统一→母语润色→排版）、视频字幕、数据处理管道
- **风险**：链路断裂（中间一环出错，下游全部作废）。需严格约定输入/输出格式

### 树形分层

```
            Lead
         ┌───┴───┐
       组长A    组长B       ← 组长向Lead汇报
       ┌┴┐     ┌┴┐
      B1 B2   B3 B4        ← 下层向组长汇报，下层间不通信
```

- **机制**：上层指派任务+接收回报并综合判断，下层之间不通信。每层只处理匹配其抽象层次的信息
- **适用**：大规模并行（8+ Agent），Lead 直接管理所有人不可行
- **案例**：大型活动策划（总策划→场地/内容组长→具体执行）、软件系统迁移、多语种本地化
- **风险**：组长瓶颈——组长只是转发不做判断则退化为星型。组长能力必须明显强于下层。Agent 总数 8+

## 选择决策表

| 你的任务特征 | 推荐模式 | 一句话理由 |
|---|---|---|
| "同一件事，需要多个独立视角" | 星型单轮 | 并行独立分析，Lead 找交叉和矛盾 |
| "只需要收集信息，我自己判断" | 数据采集器 | Agent 不做判断，只当搜索引擎 |
| "分几个阶段，后一步依赖前一步结果" | 流水线多轮 | 阶段间 Lead 中转，阶段内并行 |
| "需要不同观点正面交锋" | 网状辩论 | 让对立立场互相对抗，Lead 裁决 |
| "一个产出物要经过多道工序精炼" | 链式接力 | 像流水线，每道工序只做一件事 |
| "活太多，我一个人管不过来" | 树形分层 | 设组长，分层调度 |
| **"大表 + 规则可脚本化 + LLM 语义判断"** | **8 阶段流水线（模式 B）** | 流水线多轮的预设深化，见 layered-pipeline.md |

**流水线多轮 vs 链式接力的选择**：
- 阶段间需要**综合多份产出**再分派 → 流水线多轮（Lead 做中转）
- 阶段间是**一对一递进**，上一步产出直接喂下一步 → 链式接力（Agent 直接交接）

## 混合模式

复杂任务通常需要混合使用：

- **树形 + 星型**：树形的每个叶子节点内用星型（多个独立分析员并行），组长综合后上树。适合"大规模+深分析"——如多产品线的竞品调研
- **链式 + 辩论**：链式精炼到最终产出后，加一个辩论环节检验结论。适合"高精度+高风险"——如重要合同条款审查、关键算法设计评审
- **星型 + 链式**：先用星型并行收集多维度信息，再用链式逐级加工成最终产出。适合"广撒网+深度加工"——如市场分析报告撰写
- **流水线 + 星型 → 8 阶段**：8 阶段分层流水线正是"流水线多轮 + 阶段内星型"的固定混合，工程化后直接复用

## 总结

```
无通信                              有通信
─────────────────                  ─────────────────
核心取舍：                           核心取舍：
独立 > 效率                          灵活 > 简单
Agent不需要知道别人在想什么           Agent需要互相知道、互相影响

适合：                               适合：
- 视角可以独立并行                    - 产出有依赖关系
- 需要保持判断的独立性                - 需要观点碰撞
- 追求系统简单、可预测                - 任务规模超出单人管理能力

一句话记忆：
无通信 = 多双眼睛看同一件事，各看各的
有通信 = 多双手加工同一件事，接力或对抗
```
