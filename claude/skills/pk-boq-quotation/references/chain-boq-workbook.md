## BOQ 工作簿：填报员改用脚本，不逐条读

> **状态：提取脚本 `scripts/import/boq/extract_boq_manifest.py` 尚未落地**（实施计划见
> `E:\Code\CostSpread\docs\boq-excel-import-plan.md`）。落地前 BOQ 工作簿不要走本链路，
> 也不要临时手写提取代码顶上——那正是这套东西要消灭的重复劳动。
> 脚本落地后把命令行补进本小节。

分包 BOQ 与供应商报价单是两种东西，提取方式必须跟着变：

| | 供应商报价单 | 分包 BOQ 工作簿 |
|---|---|---|
| 规模 | 几十条 | 数千行 × 多 sheet |
| 价格在哪 | 散在版面里，要读 | **在固定列位上** |
| 材料价/综合价怎么分 | 靠名称与上下文判断 | **靠列位，主表头 `Unit Rate` 横向合并跨三列，副表头是 `Material \| Labour \| Total`** |
| 该谁提取 | LLM 逐条读 | 脚本按列位抽，LLM 不碰数字 |

**列位是确定性信息，让 LLM 逐条读既慢又会读错。** 一行 BOQ 最多拆出三条记录：Material 列 → 材料价、Labour 列 → 人工价、Total 列 → 综合单价，由 `dataType` 告诉分类器该判哪种 `resourceType`。

**但填报员这个角色一个字都没少。** 脚本消掉的只是"逐条读数字"，判断全都还在：

| 填报员必须判的 | 为什么脚本做不了 |
|---|---|
| `--sheets` 白名单最终确认 | 主会话给出建议（⓿ d），填报员核对工作簿实际内容后确认或提异议 |
| 报价日期 | 有的工作簿 `DATE` 单元格是空的，只能从元数据推，**推了必须标 `uncertain`** |
| 被跳过的表怎么办 | 脚本只处理 `Unit Rate` 三分列形态，其余（多分区表、开办费、厂商清单）跳过并列进 `extract-report.md`，要不要另行处理是判断题 |
| 纯位号名称算不算有效条目 | `R-ACH-1PA-01,1PB-02...` 这类只有位号没有品名的行，交回时必须点出来 |
| 供应商与专业归属 | 工作簿里往往没写，要从目录结构和合同名推 |

交回主会话时，除了 PDF 链要求的那些，还要说清：**用了哪些 sheet、为什么不用其余的、`extract-report.md` 里跳过的表各是什么情况**。

## 审核时（补 4.2）

上面那张表是为 LLM 逐条读写的——它防的是"`888` 读成 `8880`"这类**单点错读**。BOQ 走脚本，这类错不会发生：脚本按列位取数，取到就是原值。

**BOQ 的风险是整列定位错**，表现完全不同：不是某一条离谱，而是**一整片系统性地错**。所以审 `review-checklist` 时看的东西要换：

| 现象 | 判断 |
|---|---|
| 同一 sheet 内出现整片相同价格 | 多半取到了合并单元格被前向填充的列 → **整表打回**，别逐条剔 |
| 某个 sheet 的价格整体比同类高/低一个数量级 | 取错了子列（把 Amount 当成 Unit Rate，或把 Material 当成 Total）→ **整表打回** |
| 材料价 > 综合单价 | Material 与 Total 两列取反了 → **整表打回** |
| 大量条目 `unit` 相同但 `name` 是纯位号 | 该 sheet 是设备清单不是计价清单 → 应从白名单里去掉 |
| 单条价格离谱但同 sheet 其余正常 | 源数据本身就那样（BOQ 里确有 `0` 和占位行）→ 按普通异常判 |

一句话：**PDF 链逐条核对数字，BOQ 链看分布和列间关系。** 拿 BOQ 当 PDF 逐条核，既慢又抓不到真正的错。

`--analyze` 的 `analysis-report.json` 里 `resourceTypeDist` 对 BOQ 链特别有用：`composite` / `material` / `labor` 三者条数应当接近（每行拆三条），某一类明显偏少说明那一列没取到。


## 召回核对（补 4.3）

`audit-recall.js` 判"疑似报价行"的标准是**有 ≥50 的数字 + 至少 3 个非数字字符**。BOQ 的
`raw/<sheet>.md` 里，被有意跳过的行几乎全部命中这个标准：

- 汇总行 `SUMMARY MAIN BUILDING ... 319149760.70`
- 包干行 `Fuel Distribution | Ls | 1 | 24952472.68`
- 无单价行（只有工程量和合价，没填单价）

实测量级：`EE-BOQ-Building` 有效明细 453 行，而被跳过的包干行 611 行、无价行 633 行。
**覆盖率会落在 30% 上下，这是设计使然，不是漏抽。** 直接套 85% 会把每一批都误判打回。

BOQ 链改用这三条判据，比覆盖率精确得多：

| 查什么 | 怎么查 | 不达标说明 |
|---|---|---|
| **判定为 `detail` 的行必须条条被引用** | `raw/<sheet>.md` 每行带 `判定` 列，数出 `detail` 行数，与 `extract-report.md` 里该 sheet 的明细数、以及 manifest 里该 sheet 的 distinct 行号数三者比对 | 三个数对不上 = 提取器丢了记录，**打回** |
| **抽查 `no_price` 行是真没价** | 随机取 10 行回源文件看 | 源文件明明有单价却被判 `no_price` = 列定位错，**整表打回** |
| **抽查 `lumpsum` 行的单位** | 看判定为 `lumpsum` 的行，单位是否确实是 `Ls`/`Item`/`Lot`/`Sum` | 有正常单位被误判 = 单位归一化出错，**打回** |

第一条是 BOQ 链真正的召回指标，**它比覆盖率更严**：要求 100% 而不是 85%。


## 质量标准（补）

- **无整项价泄漏**（`unit` 不含 `Ls`/`Item`/`Lot`/`Sum`）
- **`resourceTypeDist` 里 `composite`/`material`/`labor` 三者条数接近**（每行拆三条，某类明显偏少说明有一列没取到）
- **用了哪些 sheet、为什么不用其余的，已写进 `review-notes.md`**
