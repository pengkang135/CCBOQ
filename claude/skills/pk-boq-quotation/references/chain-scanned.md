## 纯扫描件：价格的三档采信

纯图片报价单不在少数，而且**那份签了字盖了章的扫描件往往才是定稿**，比 Excel 草稿更权威。所以这条链路不是权宜之计，是正路。

```bash
python "...\scripts\scan_price_table.py" <扫描件.pdf> --page 1 --rel 0.08,0.15,0.86,0.42
python "...\scripts\scan_price_table.py" <扫描件.pdf> --page 1 --engines rapid   # 快速迭代，跳过慢的 paddle
```

先用 `extract_region.py --thumb` 看整页定位表格区域，再用 `--rel` 把表格圈给它。

**每个数字走它能走到的最高档，档位写进 manifest 的 `priceVerify`：**

| 档 | 条件 | 判定 |
|---|---|---|
| `arith` | 行内 `数量×单价=总价`、列求和、比例关系闭合 | **确定性证明**，直接采信 |
| `dual` | 无算术冗余，但 rapidocr 与 paddleocr 读数一致 | 采信，注明仅多源一致 |
| `none` | 双引擎分歧或只有单引擎读到 | 填最可能值 + 标 `uncertain`，写清分歧内容 |

**算术闭合为什么是这套设计的核心**：注入 `508 → 503`（字形相近、量级正常、和历史价比也合理），双引擎可能一起读错、人工核对也发现不了，但乘积当场对不上，**而且定位到是哪一行哪个字段**。这不是统计推断，是证明。

两个引擎是互补不是重复，实测同一张表：

| | 中文 | 数字 |
|---|---|---|
| `rapidocr` | 全对 | 全对但置信度低（`80` 仅 0.52） |
| `paddleocr lang='en'` | 全是乱码 | 全对且置信度 1.00 |

脚本按 bbox 重建行列，用**组合搜索**找 `a×b=c`——不按大小猜谁是数量谁是单价（实测那张表数量 12213.5 就比单价 157 大，猜必错），而是按列序指派并标 `assignedBy: column-order`，填报员对照表头确认后再写 manifest。

脚本还会自动打标四类不可入库行：`total` 合计、`provisional` 暂定金额、`lumpsum` 实报实销、`conditional` 如有/若发生。**打标不等于判定**，逐行看过再决定。

> 实测基准：一份孟加拉国清关物流报价（手机拍照件、无文本层、1 页 6 行）
> 全部 14 个数字 `arith` 12 个、`dual` 2 个、`none` 0 个，三条结构性冗余全部闭合。
> 这份成像质量偏好，**倾斜、印章压字、手写改价的样本还没测过**，遇到时按实际情况补预处理。

## 审核时（补 4.2）

上面那张表的第一条「解析值不在原文数字里 → 剔除」在这条链上失效——**没有"原文数字"可比，OCR 读数就是唯一的原文读法**。改看这三条：

| 现象 | 判断 |
|---|---|
| 某条 `priceVerify=none` 但填报员没标 `uncertain` | 交叉验证的结论被无视了 → **打回** |
| 整表 `arith` 占比为 0，而表里明明有数量和总价列 | 版面重建失败（列没对齐/表格线断） → **整表打回重跑，别逐条剔** |
| `arith` 闭合但价格离谱 | **保留**——算术闭合说明读数忠于原件，离谱是源数据本身的事，按普通异常判 |
| 命中 `provisional`/`lumpsum`/`total` 标记的行被填进了 manifest | 不可入库项泄漏 → **剔除** |

召回核对同样不适用：纯扫描件没有 `raw/*.md` 可反向比对。用 `scan_price_table.py` 输出的**版面行数 vs manifest 条数**代替覆盖率，差额必须逐行有交代（表头、合计行、实报实销行各几条）。
