# xlsx_purge.py 实现笔记

改脚本前先看这里。以下每一条都对应过一个真实踩过的坑，回归测试覆盖了它们。

## 解析

**1. 自闭合 `<f/>` 会吞掉后面的公式**

`<f t="shared" si="17"/>` 用 `<f\b([^>]*)>` 去匹配，`[^>]*` 会把结尾的 `/` 吃进属性，于是它被当成开标签，`(.*?)</f>` 一路吞到下一个单元格的 `</f>`，把中间夹着的真公式整段吃掉。

光在结果里跳过自闭合位置没用 —— `finditer` 已经把那段文本消耗掉了，被吞的公式再也匹配不到。属性部分必须写成 `(?:[^>/]|/(?!>))*`。

实测影响：2707 个外链公式清不掉，同时 `collect_live` 漏扫这些公式导致名称在用判定失真。

**2. 名称正则必须用 `\w` 而不是 `[A-Za-z0-9_]`**

定义名称可以是中文、泰文、韩文。用 ASCII 字符类会让「B价」这种名称永远匹配不上，被判成没人引用而删掉 —— 静默的数据损坏。实测一个文件里 7254 个候选名称中有 749 个非 ASCII。

**3. 字符串常量在 XML 里是 `&quot;`**

sheet XML 的 `<f>` 内容里，公式的 `"文本"` 存成 `&quot;文本&quot;`。剥离引号的正则只认裸 `"` 的话，常量内容会被当标识符扫进去。

## 匹配

**4. 公式里的 `AA:AA`、`$AB$24` 不是名称**

不排除单元格引用形式，就会拿列标去撞同名的待删名称，把根本不碰外链的公式一起粘死。

Excel 本来就不允许把名称定义成单元格引用形式（建名称时就拦掉了），所以形如合法列名/单元格地址的标识符一律不是名称引用。判定要检查列号 ≤ 16384、行号 ≤ 1048576。

实测影响：修复前粘死 40914 格，修复后 11052 格（正好等于实际 `[N]` 引用数），有 29862 格正常公式是被误伤的。

**5. `Table1[列名]` 不是外部引用**

判外部要看 `[...]` 里装的是什么：纯数字索引、工作簿扩展名、带路径分隔符才算外部。结构化表引用的列名不算。

**6. 外部性要沿名称链传播**

名称 A 的 body 引用了指向外表的名称 B，删掉 B 之后 A 一样会坏。不传播的话清完外链还剩一批 `#NAME?`。

**7. 待删名称集合只放外部/坏/垃圾三类**

没人引用的名称不进这个集合。万一在用判定漏了，也不至于大面积粘死正常公式 —— 宁可留个孤名，不可毁一片公式。

**13. 名称引用不止出现在公式里**

透视表的数据源是 pivotCacheDefinition 里的 `<worksheetSource name="X"/>` —— 一个直接的名称引用，不在任何 sheet 的公式中。只扫 sheet 就会把它判成孤名删掉，文件还能打开、透视表看着也在，但数据源已经断了，一刷新就空。

同类的还有图表 `<c:f>`、表格的 `calculatedColumnFormula` / `totalsRowFormula`、queryTable 和 connections。这些 part 一并读进来补全在用判定（只读不改）。

`worksheetSource` 的 name 要按属性值直接查名称表，不能走标识符扫描 —— 它不是公式，里面就是个裸名称。

pivotCacheRecords 不含名称引用且动辄上百 MB，别扫。

实测影响：一个带 4 个透视表的模板，「分类定义区」被当 unused 删掉，下游每次都要重建才能用。

## 转值

**8. 空字符串结果存成自闭合 `<v/>`**

只认 `<v>...</v>` 会把这一格当成「没有值」清空，`''` 变成真空单元格。实测 5022 格受影响。

**9. `t="str"` 删掉 `<f>` 后属性就不合法**

`t="str"` 的含义是「公式返回字符串」，没有 `<f>` 时 Excel 会报修复。必须改写成 `t="inlineStr"` + `<is><t xml:space="preserve">`。

**10. shared formula 整组一起转**

master 被转值后，`<f t="shared" si="N"/>` 的 slave 就成了没有主的孤儿，Excel 打开报修复。master 命中时要把同 si 的 slave 一并转掉。

## 性能

**11. 两处不能写成 O(n²)**

- 定位单元格边界用 `text.find('</c>', pos)`，不要切片 `text[end:]`
- 所有替换攒成 ops 排序后一次 `''.join()`，不要逐个 `text = text[:s] + rep + text[e:]`

6MB 的 sheet 配上万条外链公式，这两处写错要跑 60 秒，改成线性后 1.5 秒。

**12. 只解压需要改的 part**

workbook.xml、sheet、rels、Content_Types 读进内存，其余（sharedStrings、media、styles）在写出时流式转存。

**14. 瓶颈不在脚本，别再优化脚本了**

实测一个 2482KB / 41 sheets / 102107 条定义名称 / 43 万单元格的真实 BOQ：

| 阶段 | 耗时 |
|------|------|
| unzip+decode | 0.038s |
| `parse_defined_names` | 0.188s |
| `propagate_external` | 0.286s |
| `build_lookup` | 0.069s |
| `collect_live` | 0.059s |
| `propagate_live` | 0.019s |
| **purge 全程** | **约 1s** |
| **verify 全程** | **约 2s** |

名称有 10 万条，但 `build_lookup` 先把外部/坏/垃圾筛掉了，`lookup` 只剩 1794 条、`live` 只有 2 条、公式 12312 条 —— 在用判定才花 0.059s。**名称多不等于在用判定贵。**

据此提过一个「fast 档跳过在用判定」的方案，实测只省 0.147s，而 precise 多花这点时间能多清 8056 个孤名，划算得多，方案作废。同期验证过：`--mode links` 下 `collect_live` 的结果只影响统计标签（`kept_used` vs `kept_unused`），不影响输出文件一个字节 —— 跳过它产物逐字节相同。想再动这块之前先看这条。

也试过「`propagate_external` 跳过已 external 的 entry」，无效（1.0x）：external 只有 679 条，那 9 万多条待删名称绝大多数是 junk/broken，body 照样得逐条检查。

真正慢的是 AI 的操作流程。同一批文件人工走一遍花了 276 秒，其中脚本占 2.4 秒，180 秒耗在现写验证脚本和排查假阳性上。所以有了 `verify.py`，见下条。

## 验证

**15. 值比对绝不能用 fastexcel / openpyxl 读回来比**

Excel 读库会做 dtype/NaN 推断，同一份数据读两遍能给出几十格假 differ。踩过一次：报了 40 格 differ，换 openpyxl `data_only` 才确认 41181 格其实一格没变，来回折腾三分钟。

正确做法是比对 XML 层的缓存值 —— 转值就是删 `<f>` 留 `<v>`，值变没变在 XML 里看得一清二楚，零推断零假阳性，而且 sheet XML 本来就已经解压在内存里。`verify.py` 的 `cell_values()` 就是这么做的，注意三处归一：`t="s"` 要解引用 sharedStrings、`t="str"` 转 `inlineStr` 后值从 `<v>` 挪到了 `<is><t>`、数值文本 `"1.0"` 与 `"1"` 要按 float 归一。

XML parse 检查同理不能只查产物：`customXml/item*.xml` 之类的 part 常常声明 UTF-8 实为 UTF-16 BOM，原文件就 parse 不了，原样转存也不会变好。必须对比着查，只报「原来能 parse、现在不能」的。
